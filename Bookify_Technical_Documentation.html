1. Android Activity Lifecycle

1.1 What Is an Activity?

In Android development, an Activity is the single most important building block of any app. It represents one screen with a user interface. Every Android app must have at least one Activity declared in its AndroidManifest.xml. When the user taps the app icon on their phone, Android creates an instance of the main (launcher) Activity and the app starts.

Bookify uses a Single-Activity Architecture — the entire app (all 8 screens, all navigation, all logic) lives inside one Activity class called MainActivity. The different screens are not separate Activities; they are Jetpack Compose functions that swap in and out inside the same Activity. This is the modern recommended approach for Android apps.

1.2 The Lifecycle — How Android Manages Your Activity

Android controls when your Activity is created, shown, hidden, and destroyed. It does this through a set of lifecycle callback methods that Android automatically calls as the app changes state. As a developer, you override these methods to run your own code at the right moment.

The lifecycle follows this order:

OrderMethodWhen Android Calls ItWhat It Means
1 onCreate() The very first time the Activity is created App is starting up — initialise everything here
2 onStart() Activity is about to become visible Screen is becoming visible but not yet interactive
3 onResume() Activity is fully visible and in the foreground User can now tap and interact with the app
4 onPause() Another app/dialog is partially covering this one App is still partially visible but losing focus
5 onStop() Activity is fully hidden (user pressed Home) App is in the background — not visible at all
6 onDestroy() Activity is being permanently shut down App is closing — release all resources here
The golden rule: Every lifecycle method must call super.methodName() as its first line. If you forget this, Android's internal setup code will not run and the app will behave incorrectly or crash.

1.3 How Bookify Implements the Lifecycle

Below is the complete MainActivity.kt showing all six lifecycle methods as implemented in the Bookify app. Each method is explained in the subsections that follow.

class MainActivity : ComponentActivity() {

    // Database declared at Activity level so all lifecycle methods can access it
    private lateinit var db: DatabaseHelper

    // ── LIFECYCLE METHOD 1: onCreate ───────────────────────────
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        Log.d("BookifyLifecycle", "onCreate: App is starting")
        db = DatabaseHelper(this)
        enableEdgeToEdge()
        setContent {
            BookifyTheme { BookifyApp(db) }
        }
    }

    // ── LIFECYCLE METHOD 2: onStart ────────────────────────────
    override fun onStart() {
        super.onStart()
        Log.d("BookifyLifecycle", "onStart: App is now visible to the user")
    }

    // ── LIFECYCLE METHOD 3: onResume ───────────────────────────
    override fun onResume() {
        super.onResume()
        Log.d("BookifyLifecycle", "onResume: App is in the foreground — user can interact")
    }

    // ── LIFECYCLE METHOD 4: onPause ────────────────────────────
    override fun onPause() {
        super.onPause()
        Log.d("BookifyLifecycle", "onPause: App is partially hidden")
    }

    // ── LIFECYCLE METHOD 5: onStop ─────────────────────────────
    override fun onStop() {
        super.onStop()
        Log.d("BookifyLifecycle", "onStop: App is no longer visible")
    }

    // ── LIFECYCLE METHOD 6: onDestroy ──────────────────────────
    override fun onDestroy() {
        super.onDestroy()
        db.close()
        Log.d("BookifyLifecycle", "onDestroy: App is closing — database closed")
    }
}
How to see this working: Open Android Studio → Logcat tab → filter by tag BookifyLifecycle. Then press Home, switch apps, rotate the phone — you will see each method logged in real time.

1.4 onCreate() — Starting the App

onCreate() is the most important lifecycle method. It runs exactly once when the Activity is first created. This is where we set up everything the app needs to run.

What we do in Bookify's onCreate():

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)       // ① Must always call this first
    Log.d("BookifyLifecycle", "onCreate: App is starting")

    db = DatabaseHelper(this)               // ② Open the SQLite database
    enableEdgeToEdge()                        // ③ Draw behind status/nav bar

    setContent {                              // ④ Attach Compose UI to Activity
        BookifyTheme {
            BookifyApp(db)                   // ⑤ Pass db into the UI
        }
    }
}
  • ① super.onCreate() — Calls the parent class setup. Always required as the first line or the app will crash.
  • ② DatabaseHelper(this) — Opens the SQLite database once at startup. The this keyword passes the Activity as a Context, which Android needs to find the app's storage folder. The database stays open for the entire lifetime of the Activity and is closed in onDestroy().
  • ③ enableEdgeToEdge() — Tells Android to allow the app to draw under the status bar and bottom navigation bar, giving Bookify its dark full-screen look.
  • ④ setContent { } — This is the bridge between Android and Jetpack Compose. It replaces the traditional setContentView(R.layout.activity_main) call. Everything inside is Compose UI, not XML.
  • ⑤ BookifyApp(db) — Passes the single shared database instance into the entire Compose UI tree so all screens can use the same connection.

1.5 onStart() — App Becomes Visible

onStart() is called immediately after onCreate(), and also every time the app returns from a fully hidden state (e.g. user comes back from another app). At this point the screen is visible but the user cannot interact with it yet.

override fun onStart() {
    super.onStart()
    Log.d("BookifyLifecycle", "onStart: App is now visible to the user")
}

When this fires in Bookify:

  • The moment the app first launches (straight after onCreate)
  • When the user presses the Recent Apps button and then taps back into Bookify
  • When a phone call ends and the user returns to the app
In Bookify we only log here. In a more advanced app you might restart a location listener or refresh data from a server — things you stopped in onStop().

1.6 onResume() — App is Interactive

onResume() is called after onStart() and means the Activity is now in the foreground and the user can fully interact with it — touching buttons, scrolling, typing. This is the state the app is in for most of its life.

override fun onResume() {
    super.onResume()
    Log.d("BookifyLifecycle", "onResume: App is in the foreground — user can interact")
}

When this fires in Bookify:

  • Right after onStart() when the app first opens
  • After a system dialog (like a permission prompt) is dismissed
  • After the user returns from pressing Home or switching away
Normal app usage — browsing events, booking tickets, navigating between screens — all happens while the app is in the Resumed state.

1.7 onPause() — App Partially Hidden

onPause() is called when the Activity is still partially visible but is no longer in focus. This happens when a dialog appears on top of the app, or when the user starts swiping to another app. The Activity is still running but the user is not actively using it.

override fun onPause() {
    super.onPause()
    Log.d("BookifyLifecycle", "onPause: App is partially hidden")
}

When this fires in Bookify:

  • When the booking confirmation AlertDialog appears over the Event Detail screen
  • When the user starts the gesture to swipe to another app
  • When a phone call notification drops down from the status bar
Important: onPause() must execute quickly. Android may kill the process shortly after this method returns if system resources are low. Never do heavy work (network calls, database writes) in onPause().

1.8 onStop() — App Fully Hidden

onStop() is called when the Activity is completely invisible to the user. This happens when the user presses the Home button, switches to another app, or when a new Activity fully covers this one.

override fun onStop() {
    super.onStop()
    Log.d("BookifyLifecycle", "onStop: App is no longer visible")
}

When this fires in Bookify:

  • User presses the Home button — Bookify goes to the background
  • User switches to WhatsApp or another app from the Recents screen
  • Phone screen turns off

The app's data is safe because it is stored in SQLite on disk. The database connection stays open — we only close it in onDestroy() because we want the database to remain accessible when the user comes back.

1.9 onDestroy() — App is Closing

onDestroy() is the last lifecycle method called before the Activity is permanently shut down. This is the place to release any resources that would otherwise cause a memory leak.

override fun onDestroy() {
    super.onDestroy()
    db.close()    // close the SQLite database connection
    Log.d("BookifyLifecycle", "onDestroy: App is closing — database closed")
}

When this fires in Bookify:

  • User swipes the app off the Recents screen (force-close)
  • The app calls finish() (not used in Bookify, but possible)
  • Android kills the process to recover memory

Why db.close() here? The DatabaseHelper holds a reference to an open SQLite file. If we never close it, the file handle leaks. By closing it in onDestroy(), we match the database lifetime to the Activity lifetime — it opens in onCreate() and closes in onDestroy().

Note on screen rotation: Rotating the phone causes Android to destroy and recreate the Activity. This is why we use rememberSaveable (not just remember) for the current screen name and selected tab — so those values survive the rotation and the user stays on the same screen.

1.11 rememberSaveable vs remember — Surviving Rotation

Because rotation destroys and recreates the Activity, any state stored in plain remember { } is lost. We upgraded the navigation state variables to use rememberSaveable which persists values across configuration changes:

@Composable
fun BookifyApp(db: DatabaseHelper) {

    // rememberSaveable — survives rotation (screen & tab are basic types)
    var screen      by rememberSaveable { mutableStateOf("splash") }
    var selectedNav by rememberSaveable { mutableIntStateOf(0) }

    // remember only — User and Event are not simple types, so they reset on rotation
    var currentUser: User?  by remember { mutableStateOf(null) }
    var selectedEvent: Event? by remember { mutableStateOf(null) }
    // ...
}
VariableType UsedSurvives Rotation?Why
screen (e.g. "home")rememberSaveable✅ YesString is a primitive — can be saved automatically
selectedNav (0–3)rememberSaveable✅ YesInt is a primitive — can be saved automatically
currentUserremember❌ NoCustom class — would need Parcelable to save; user must log in again after rotation
selectedEventremember❌ NoCustom class — event detail is lost on rotation but the user returns to Home safely

1.12 Database Tied to Activity Lifecycle

One of the key design decisions in Bookify is that the DatabaseHelper is managed entirely by the Activity lifecycle. It is declared as a class-level property and opened/closed at the right lifecycle moments:

class MainActivity : ComponentActivity() {

    private lateinit var db: DatabaseHelper   // declared here, not inside any screen

    override fun onCreate(...) {
        db = DatabaseHelper(this)              // opened once when app starts
        setContent { BookifyTheme { BookifyApp(db) } }  // passed to all screens
    }

    override fun onDestroy() {
        super.onDestroy()
        db.close()                              // closed once when app ends
    }
}

The db instance is then passed as a parameter from BookifyApp() down into every screen that needs it — LoginScreen(db), HomeFeedScreen(db), EventDetailScreen(db), etc. This means there is always exactly one database connection for the entire app lifetime — no connection is accidentally left open or opened twice.

1.13 AndroidManifest.xml — Registering the Activity

Every Activity must be listed in AndroidManifest.xml. Without this registration, Android will not know the Activity exists and will refuse to launch it. The intent-filter block marks it as the launcher — the screen that appears when the user taps the Bookify icon:

<!-- app/src/main/AndroidManifest.xml -->
<application
    android:label="Bookify"
    android:theme="@style/Theme.Bookify">

    <activity
        android:name=".MainActivity"
        android:exported="true">

        <intent-filter>
            <action android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LAUNCHER" />
        </intent-filter>
    </activity>

</application>
  • android:name=".MainActivity" — The dot prefix means it is inside the app's own package (com.example.bookify.MainActivity).
  • android:exported="true" — Required on Android 12+ for any Activity with an intent-filter. Without it the build fails.
  • action.MAIN + category.LAUNCHER — Together these two lines tell Android: "this is the Activity to open when the user taps the app icon."

3. Data Layer — Where Data is Stored

All data is stored in an on-device SQLite database named bookify.db. Android places this file at:

/data/data/com.example.bookify/databases/bookify.db
This is private to the app — no external app can access it without root.

The database is managed by a class called DatabaseHelper which extends Android's built-in SQLiteOpenHelper.

3.3 DatabaseHelper — Creating the Tables

The onCreate() method runs exactly once when the database is first created on the device. It creates all three tables and calls seedEvents() to pre-load sample data.

class DatabaseHelper(context: Context) :
    SQLiteOpenHelper(context, "bookify.db", null, 1) {

    override fun onCreate(db: SQLiteDatabase) {
        db.execSQL("""
            CREATE TABLE users (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                fullName TEXT NOT NULL,
                email TEXT NOT NULL UNIQUE,
                password TEXT NOT NULL,
                phone TEXT NOT NULL
            )
        """)

        db.execSQL("""
            CREATE TABLE events (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                title TEXT NOT NULL,
                location TEXT NOT NULL,
                date TEXT NOT NULL,
                time TEXT NOT NULL,
                category TEXT NOT NULL,
                price TEXT NOT NULL,
                slotsLeft INTEGER NOT NULL,
                description TEXT NOT NULL,
                isPrivate INTEGER NOT NULL DEFAULT 0,
                inviteCode TEXT,
                cardColorHex TEXT NOT NULL
            )
        """)

        db.execSQL("""
            CREATE TABLE bookings (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                userId INTEGER NOT NULL,
                eventId INTEGER NOT NULL,
                ticketNo TEXT NOT NULL,
                status TEXT NOT NULL DEFAULT 'upcoming'
            )
        """)

        seedEvents(db)  // Insert demo events on first launch
    }
}

4. Navigation & Screen Routing

Bookify has a single Activity (MainActivity) — the entire app is driven by Jetpack Compose. Instead of multiple Activities or Fragments, we use a single @Composable function called BookifyApp() that holds a screen state variable and switches what is shown using a when expression. This pattern is called state-driven navigation.

4.1 MainActivity

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        enableEdgeToEdge()   // draw behind system bars
        setContent {
            BookifyTheme {
                BookifyApp()
            }
        }
    }
}
enableEdgeToEdge() tells Android to let the app draw underneath the status bar and navigation bar, giving the modern full-bleed look seen in the mockups.

4.2 BookifyApp — The Navigation Controller

@Composable
fun BookifyApp() {
    // State variables — changes to these trigger recomposition
    var screen       by remember { mutableStateOf("splash") }
    var currentUser: User? by remember { mutableStateOf(null) }
    var selectedNav  by remember { mutableIntStateOf(0) }
    var selectedEvent: Event? by remember { mutableStateOf(null) }

    // Physical back button handling
    BackHandler(enabled = screen == "detail" || screen == "login") {
        screen = if (screen == "detail") "home" else "splash"
    }

    when (screen) {
        "splash"   -> SplashScreen(
            onGetStarted = { screen = "register" },
            onLogin      = { screen = "login" }
        )
        "login"    -> LoginScreen(
            onLoginSuccess      = { user -> currentUser = user; screen = "home" },
            onNavigateToRegister = { screen = "register" }
        )
        "register" -> RegisterScreen(
            onRegisterSuccess   = { user -> currentUser = user; screen = "home" },
            onNavigateToLogin   = { screen = "login" }
        )
        "home"     -> { /* bottom nav routing — see section 3.3 */ }
        "detail"   -> EventDetailScreen(
            event          = selectedEvent!!,
            currentUser    = currentUser,
            onBack         = { screen = "home" },
            onBookingSuccess = { selectedNav = 2; screen = "home" }
        )
    }
}

Each screen composable receives callback lambdas instead of knowing about the navigation directly. This keeps every screen isolated — a screen just calls onLoginSuccess(user) and the controller decides what to do next.

4.3 Bottom Navigation Routing

Inside the "home" case, a second when on selectedNav (0–3) selects which screen to show:

"home" -> {
    when (selectedNav) {
        0, 1 -> HomeFeedScreen(
            currentUser  = currentUser,
            selectedNav  = selectedNav,
            onNavSelected = { selectedNav = it },
            onEventClick  = { event -> selectedEvent = event; screen = "detail" }
        )
        2 -> TicketsTabScreen(
            currentUser  = currentUser,
            selectedNav  = selectedNav,
            onNavSelected = { selectedNav = it },
            onEventFound  = { event -> selectedEvent = event; screen = "detail" }
        )
        3 -> ProfileScreen(
            currentUser  = currentUser,
            onLogout     = { currentUser = null; selectedNav = 0; screen = "splash" },
            onLoginRequest = { screen = "login" }
        )
    }
}

5. Frontend — Jetpack Compose UI

The entire UI is built with Jetpack Compose, Android's modern declarative UI toolkit. Instead of XML layouts, every screen is a Kotlin function annotated with @Composable. The UI automatically re-renders whenever state changes.

5.3 Shared Text Field Component

5.4 Home Feed Screen

The Home feed uses a LazyColumn — Android's efficient scrollable list that only renders visible items. Inside it, the header, search bar, category chips, and event cards are each wrapped in item { } blocks:

LazyColumn(modifier = Modifier.fillMaxSize()) {
    item { /* Greeting header */ }
    item { /* Search bar */ }
    item {
        // Category chips in a horizontal scroll row
        LazyRow(horizontalArrangement = Arrangement.spacedBy(8.dp)) {
            items(allCategories.size) { i ->
                val selected = allCategories[i] == selectedCategory
                Box(
                    modifier = Modifier
                        .clip(RoundedCornerShape(50))
                        .background(if (selected) PrimaryPurple else ChipBg)
                        .clickable { selectedCategory = allCategories[i] }
                        .padding(horizontal = 18.dp, vertical = 8.dp)
                ) {
                    Text(allCategories[i], color = if (selected) Color.White else TextMuted)
                }
            }
        }
    }
    items(displayed.size) { i ->
        EventFeedCard(event = displayed[i], onClick = { onEventClick(displayed[i]) })
    }
}

Events are loaded from SQLite via db.getAllPublicEvents() inside a remember { } block so the query only runs once per composition, not on every recomposition:

val db     = remember { DatabaseHelper(context) }
val events = remember { db.getAllPublicEvents() }

6.2 Database Insert

fun registerUser(fullName: String, email: String, password: String, phone: String): Boolean {
    return try {
        val cv = ContentValues().apply {
            put("fullName", fullName)
            put("email", email)
            put("password", password)
            put("phone", phone)
        }
        // insert() returns -1 if the UNIQUE constraint on email is violated
        writableDatabase.insert("users", null, cv) != -1L
    } catch (e: Exception) {
        false
    }
}
Note: Passwords are currently stored as plain text. In a production app, use bcrypt or Android's KeyStore + hashing before storing any credentials.

7.3 Database Query

fun loginUser(email: String, password: String): User? {
    val cursor = readableDatabase.rawQuery(
        "SELECT * FROM users WHERE email=? AND password=?",
        arrayOf(email, password)
    )
    return if (cursor.moveToFirst()) {
        val user = User(
            id       = cursor.getInt(cursor.getColumnIndexOrThrow("id")),
            fullName = cursor.getString(cursor.getColumnIndexOrThrow("fullName")),
            email    = cursor.getString(cursor.getColumnIndexOrThrow("email")),
            phone    = cursor.getString(cursor.getColumnIndexOrThrow("phone"))
        )
        cursor.close()
        user
    } else {
        cursor.close()
        null       // null signals login failure to the UI
    }
}
Parameterised queries (? placeholders with a separate argument array) are used to prevent SQL injection attacks. Never concatenate user input directly into a query string.

8.3 bookEvent() — The Database Transaction

fun bookEvent(userId: Int, eventId: Int): String? {
    // Generate a ticket number like BKF-2025-4817
    val ticketNo = "BKF-2025-${(1000..9999).random()}"

    val cv = ContentValues().apply {
        put("userId",   userId)
        put("eventId",  eventId)
        put("ticketNo", ticketNo)
        put("status",   "upcoming")
    }

    val insertedId = writableDatabase.insert("bookings", null, cv)

    if (insertedId != -1L) {
        // Decrement the available slots for this event
        writableDatabase.execSQL(
            "UPDATE events SET slotsLeft = slotsLeft - 1 WHERE id=?",
            arrayOf(eventId)
        )
    }

    return if (insertedId != -1L) ticketNo else null
}

8.4 Duplicate Booking Prevention

fun isAlreadyBooked(userId: Int, eventId: Int): Boolean {
    val cursor = readableDatabase.rawQuery(
        "SELECT id FROM bookings WHERE userId=? AND eventId=?",
        arrayOf(userId.toString(), eventId.toString())
    )
    val result = cursor.moveToFirst()
    cursor.close()
    return result   // true = row exists = already booked
}

This result is checked when the Event Detail screen opens. If true, the Book ticket button renders in green with the text "✓ Already booked" and is disabled.

10. My Tickets

The My Tickets screen fetches all bookings for the current user using a SQL JOIN between the bookings and events tables. This avoids making two separate queries and returns all display data in one call:

fun getUserBookings(userId: Int): List<Booking> {
    val list   = mutableListOf<Booking>()
    val cursor = readableDatabase.rawQuery("""
        SELECT b.id, b.ticketNo, b.status,
               e.title, e.date, e.time, e.category, e.cardColorHex
        FROM   bookings b
        JOIN   events   e ON b.eventId = e.id
        WHERE  b.userId = ?
        ORDER  BY b.id DESC
    """, arrayOf(userId.toString()))

    while (cursor.moveToNext()) {
        list.add(Booking(
            id            = cursor.getInt(0),
            ticketNo      = cursor.getString(1),
            status        = cursor.getString(2),
            eventTitle    = cursor.getString(3),
            eventDate     = cursor.getString(4),
            eventTime     = cursor.getString(5),
            eventCategory = cursor.getString(6),
            cardColorHex  = cursor.getString(7)
        ))
    }
    cursor.close()
    return list
}

On the UI side, bookings are split into Upcoming and Past lists using a simple Kotlin filter, and the active tab controls which list is shown:

val upcoming  = bookings.filter { it.status == "upcoming" }
val past      = bookings.filter { it.status == "past"     }

12. Summary

Bookify implements a complete CRUD lifecycle:

Create — Register user, book event, generate ticket
Read — Load public events, load user bookings, look up private events
Update — Decrement event slots on booking
Delete — (Logout clears session state in memory — no DB delete needed)

All data lives in a single SQLite file on the device (bookify.db) with three relational tables: users, events, and bookings. The app is fully offline-capable with no network dependency.

The UI is 100% declarative Jetpack Compose — no XML, no ViewBinding, no RecyclerView. State flows down from BookifyApp() through callbacks, keeping screens loosely coupled and testable.
